Six patterns, each where the domain actually needs it

Four are mandatory, Command is our extra, Strategy is a stretch goal that lifts us to six. Each card is also the mini class diagram you redraw in Visual Paradigm.

MVC

required
Where
MainView only draws and forwards clicks; PlannerController validates and calls the model; MealPlannerDB, WeekPlan and GroceryList hold state and fire PropertyChange events.
Why here
Same split as lab 5, so the GUI can be swapped or tested without JavaFX.
Be ready for
Who calls whom, and how does the view learn about a change it did not cause (e.g. an undo)?

Singleton (thread-safe)

required
Where
MealPlannerDB is the one place holding recipes, the week plan and the grocery list.
Why here
Every tab and the controller must see the same data; two copies would let the plan and the list drift apart.
Be ready for
Why volatile? What breaks without the second null check? How do tests reset it?

Observer (domain)

required
Where
WeekPlan keeps its own List<PlanObserver>. GroceryListGenerator implements PlanObserver and rebuilds the list on every change.
Why here
The brief says the list is "automatically generated and updated". This is a model-to-model observer, separate from MVC's PropertyChange view updates.
Be ready for
Why doesn't this count as the MVC observer? What would a second observer (PlanStats) add?

Builder

required (pick 1 creational)
Where
RecipeBuilder collects title, description, ingredients and tags, then build() validates and returns an immutable Recipe.
Why here
Recipes have many optional fields; a fluent builder beats a 6-argument constructor and makes test fixtures one line each.
Be ready for
Why Builder rather than Factory Method here? What does build() reject?

Command

your extra pattern
Where
Every plan edit is an object with execute() and undo(); CommandHistory keeps undo and redo stacks.
Why here
Planning is trial and error: Undo / Redo buttons are a real feature, and each command remembers the recipe it replaced.
Be ready for
Why does a new command clear the redo stack? What does AssignMealCommand store to undo correctly?

Strategy

stretch, optional
Where
"Fill empty slots" button: RandomFill, TagFill("vegetarian") or QuickMealsFill pick a recipe per empty slot.
Why here
Same action, swappable algorithm chosen at runtime from a dropdown. Only add it if weeks 1–3 are done.
Be ready for
How would you add a BudgetFill without touching PlannerController?

Singleton with double-checked locking

public final class MealPlannerDB {
    private static volatile MealPlannerDB instance;

    private final PropertyChangeSupport pcs =
            new PropertyChangeSupport(this);
    private final List<Recipe> recipes = new ArrayList<>();
    private final WeekPlan plan = new WeekPlan();
    private final GroceryList groceries = new GroceryList();

    private MealPlannerDB() {
        // domain Observer: the list follows the plan
        plan.addObserver(new GroceryListGenerator(groceries));
    }

    public static MealPlannerDB getInstance() {
        MealPlannerDB local = instance;
        if (local == null) {
            synchronized (MealPlannerDB.class) {
                local = instance;
                if (local == null) {
                    instance = local = new MealPlannerDB();
                }
            }
        }
        return local;
    }
}

Command with undo

public class AssignMealCommand implements Command {
    private final WeekPlan plan;
    private final DayOfWeek day;
    private final MealSlot slot;
    private final Recipe recipe;
    private Recipe previous;   // null when the slot was empty

    // constructor omitted

    @Override public void execute() {
        previous = plan.get(day, slot);
        plan.assign(day, slot, recipe);
    }

    @Override public void undo() {
        if (previous == null) plan.clear(day, slot);
        else plan.assign(day, slot, previous);
    }
}

The grocery list is the hard part; get it right first

Summing looks trivial until units, duplicates and ticked items meet. The generator normalises every ingredient to a base unit and a lower-case name, then merges.

public class GroceryListGenerator implements PlanObserver {
    private final GroceryList groceries;

    public GroceryListGenerator(GroceryList groceries) {
        this.groceries = groceries;
    }

    @Override
    public void onPlanChanged(WeekPlan plan) {
        Map<String, Quantity> totals = new TreeMap<>();
        // a List, not a Set: Pasta planned twice counts twice
        for (Recipe recipe : plan.plannedRecipes()) {
            for (Ingredient ing : recipe.ingredients()) {
                Quantity q = ing.quantity().toBase(); // 0.1 kg -> 100 g
                String key = ing.name().trim().toLowerCase()
                        + "|" + q.unit();
                totals.merge(key, q, Quantity::plus);
            }
        }
        groceries.replaceGenerated(totals); // keeps ticks + extras
    }
}
public void replaceGenerated(Map<String, Quantity> totals) {
    Set<String> ticked = generated.stream()
            .filter(GroceryItem::isBought).map(GroceryItem::key)
            .collect(Collectors.toSet());
    List<GroceryItem> old = List.copyOf(generated);
    generated.clear();
    totals.forEach((key, qty) -> generated.add(
            new GroceryItem(key, qty, ticked.contains(key), false)));
    // extras live in their own list and are not touched here
    pcs.firePropertyChange("groceries", old, List.copyOf(generated));
}

Pitfalls the tests must cover

  1. Duplicates count. plannedRecipes() returns a List, not a Set: Pasta on Monday and Thursday is 2 × 100 g.
  2. Units. Convert kg → g and l → ml before adding. Never add 2 pieces to 100 g: the key includes the base unit, so they become two lines.
  3. Names. Trim and lower-case, otherwise “Pasta ” and “pasta” are two items.
  4. Ticks survive. Regenerating must keep “bought” on items that are still needed; extras live in their own list and are never regenerated.
  5. Money-style maths. Use BigDecimal (or round for display) so 0.1 + 0.2 kg doesn’t print as 300.00000000000006 g.
  6. Deleting a planned recipe. Clear those slots first (or refuse the delete), so the plan notifies and the list shrinks.

Integration test sketch

import static java.time.DayOfWeek.*;

class PlannerIT {
    private MealPlannerDB db;
    private PlannerController controller;

    @BeforeEach
    void setUp() {
        db = MealPlannerDB.getInstance();
        db.reset();   // package-private, for tests only
        controller = new PlannerController(db, new CommandHistory());
    }

    @Test
    void pastaPlannedTwiceIsSummedAndUndoUpdatesTheList() {
        Recipe pasta = new RecipeBuilder().title("Pasta")
                .ingredient("pasta", 100, Unit.G).build();
        controller.addRecipe(pasta);
        controller.assignMeal(MONDAY, MealSlot.DINNER, pasta);
        controller.assignMeal(THURSDAY, MealSlot.DINNER, pasta);

        assertEquals(200.0, pastaGrams(), 1e-9);

        controller.undo();
        assertEquals(100.0, pastaGrams(), 1e-9);
    }

    private double pastaGrams() {
        return db.groceries().quantityOf("pasta")
                 .amount().doubleValue();
    }
}
